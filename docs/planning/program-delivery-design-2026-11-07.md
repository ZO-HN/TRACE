# Coach program, calendar, and group delivery design

Status: proposed implementation design; no schema or application change authorized by this note. Owner: TRACE maintainers. Date: 2026-11-07 (Asia/Singapore). Product decisions incorporated: coach-program/group edits automatically affect existing future delivery; standalone workout assignments remain fixed copies; social stays private by default with explicit sharing only to approved followers; AI is unavailable for V1; Android signing/device acceptance follows app completion. Scope here is only live coach program, calendar, and group delivery.

## Existing boundaries

8 November implementation note: this remains the original proposal. The [implemented program contract/evidence](../qa/live-coach-programs-2026-11-08.md) supersedes its proposed run store/eager grant materialization and date-enforcement details. Current code uses the existing performed session model, metadata-only schedule reads and on-demand immutable workout grants; the earlier [one-off calendar slice](../qa/coach-calendar-2026-11-08.md) is separate. Do not treat every proposed table/RPC or statement below as implemented.

- Coach `public.programs` is currently only a name/description/category catalog (`supabase/migrations/20260810000001_coach_workspace_features.sql`, `ProgramsPage.tsx`, `src/hooks/usePrograms.ts`). It has no ordered workout days or recipient delivery records.
- Trainee `public.workout_programs` / `program_days` / `program_enrollments` is a separate personal-program model (`supabase/migrations/20260814000000_periodized_training_programs.sql`). Its share-token flow creates a trainee-owned copy (`20260815030000_program_sharing.sql`); it is not a coach assignment mechanism and has a documented private-template reference limitation. Keep it intact.
- Coach groups and memberships already exist (`training_groups`, `training_group_members` in `20260810000001_coach_workspace_features.sql`). `program_id` currently names metadata; it does not deliver workouts. `TrainingGroupsPage.tsx` can create groups and add/remove members.
- Calendar assignments are currently React state only (`src/components/pages/CalendarPage.tsx`, `assignments` state and `setAssignments`); refresh loses them.
- Direct workout assignments already have stable operation IDs and immutable workout copies (`supabase/migrations/20261105000000_fixed_workout_assignments.sql`, `useWorkoutAssignment.ts`). Preserve this RPC and its standalone behavior unchanged.
- `workout_sessions.template_id` is nullable (`20260717000000_init_trace.sql`); mobile already has account-scoped workout drafts/outbox and the assigned-workout loader (`TRACE-client/src/hooks/useAssignedWorkout.ts`, `src/components/GymLogger.tsx`, `src/lib/outbox/`). A program-run snapshot can therefore be logged as a performed session without rewriting a standalone assigned template.

## Proposed data model

Use additive tables; retain current table meaning and row IDs.

1. **`coach_program_revisions`** — immutable saved versions for existing coach `programs`: `(id, program_id, revision_number, definition jsonb, created_by, created_at)`, unique `(program_id, revision_number)`. `definition` is a validated ordered list of stable slot IDs, week/day offsets, rest-day flags, notes, and source private-template IDs. Keep an `active_revision_id` on `programs`; update it in the same transaction as inserting a version. Each successful Save is the publication event: no separate per-client republish step. The revision records which workout goes in each slot; schedule resolution reads the source's current private workout content. Thus a source-workout save updates not-started upcoming slots automatically without rewriting the program revision.
2. **`program_deliveries`** — one active delivery per coach program and trainee: `(id, program_id, coach_id, trainee_id, start_date date, status, created_at, ended_at)`. Unique active `(program_id, trainee_id)`. `start_date` is an ISO calendar date, not a timestamp.
3. **`program_delivery_sources`** — provenance links for each effective delivery: `(delivery_id, source_kind individual|group, group_id nullable, added_at, removed_at)`. One recipient already receiving the same program through a direct assignment or another group reuses that delivery rather than seeing duplicate events. Adding/removing a group member adds/removes only that group's source; the delivery ends only when no active source remains. An individual assignment source likewise remains active through group removal.
4. **`program_occurrence_grants`** — immutable range results issued by `get_client_schedule`: `(id, delivery_id, occurrence_key, scheduled_date date, revision_id, workout_fingerprint, workout_snapshot jsonb, issued_at)`, unique `(delivery_id, occurrence_key, revision_id, workout_fingerprint)`. Fingerprint canonicalized workout content so an edited source workout can issue a new grant for the same program slot/revision while retaining the cached old grant. This makes a specific schedule snapshot an authorization for offline use. Schedule reads materialize grants only for the bounded requested range and current revision; after group removal, new reads issue no grants, but previously issued grants remain valid for pending offline work.
5. **`program_day_runs`** — immutable started/completed run records: `(id, grant_id, session_id nullable, state started|completed, started_at, completed_at)`. A run references exactly one issued grant; stable IDs make retries idempotent. A revision/group change never rewrites a grant or run. Two genuinely distinct runs remain distinct and neither is discarded.
6. **`program_delivery_operations`** — transactional idempotency ledger `(operation_id primary key, operation_kind, canonical_request jsonb, response jsonb, created_at)` for revision saves, program/group assignment, group membership, and calendar changes. Same ID/content returns the stored response; changed content fails.
7. **`coach_calendar_assignments`** — durable one-off coach calendar events with `(id, coach_id, trainee_id, scheduled_date date, assigned_template_id, status, created_at, cancelled_at)`. `assigned_template_id` is created through the existing fixed-copy operation; edits to a source template never change it. Add an index by `(trainee_id, scheduled_date)`.
8. Add nullable `program_run_id` to `workout_sessions` (unique when non-null) to tie a performed session to its captured run; keep `template_id` nullable and unchanged for program runs. The session/outbox remains the source of actual performed sets and IDs. A saved local active draft stores `program_run_id`, `grant_id`, revision ID, occurrence key, and workout snapshot so a refresh or account switch cannot replace an in-progress session.

`training_groups.program_id` remains the group's single active coach-program pointer. Add `program_start_date date` to the group for its new program's effective start. Changing the pointer/start date transactionally updates delivery rows for current members. Existing group-to-program links have no historical start date: backfill deliveries from the migration effective date, never retroactively create performed sessions.

## RPC and data access contracts

All write RPCs are `SECURITY DEFINER`, fixed `search_path`, `auth.uid()`-derived coach identity, explicit role/ownership/current-coach checks, RLS-backed reads, and `REVOKE` from anon/public. Do not authorize from client-supplied coach or member IDs alone.

- `save_coach_program_revision(operation_id, program_id, expected_revision_id, definition)` validates coach ownership, each referenced active private workout, supported bounds, and nonempty workout days; locks the program; rejects stale `expected_revision_id`; stores the immutable slot mapping and swaps `active_revision_id` atomically. Replaying the same operation and normalized content returns the original revision; changed content/owner under the same ID fails. Existing deliveries need no mutation: future schedule reads resolve the program's new active revision automatically.
- `set_training_group_members(operation_id, group_id, add_ids, remove_ids)` validates all IDs belong to the coach's current roster and changes membership plus linked program delivery sources in one transaction. New members receive the group's current program from the next not-yet-past slot in its existing cycle; do not restart Week 1 or assign already-past slots. Removed members lose future schedule access immediately; never delete run snapshots, sessions, sets, drafts, or outbox rows. A removed member's already-started/cached local session may still sync as their own performed workout, with the captured revision preserved.
- `set_group_program(operation_id, group_id, program_id nullable, start_date)` validates coach ownership and changes the active program/date. Existing members immediately resolve the latest revision; clearing the program ends future group delivery but retains run/history. Retry is exact/idempotent.
- `assign_coach_program(operation_id, program_id, trainee_id, start_date)` supports direct one-trainee delivery using the same revision resolution, with current-coach validation and idempotent retry. If an active delivery already exists through a group, add the direct source link to that delivery instead of a duplicate; a change/removal of one source must not revoke the other.
- `get_client_schedule(trainee_id, from_date, to_date)` returns authorized one-off events and program occurrences for the date range. For a not-started occurrence it resolves the delivery's latest active revision and reads each referenced source workout plus ordered items in the same transaction; for a started/completed run it returns its issued grant snapshot. In one bounded transaction, materialize/dedupe the grant rows and return their IDs/snapshots. A workout source update therefore changes upcoming grants; the old grant remains fixed. If a source workout is archived/deleted, return a visible unavailable-slot state and require the coach to replace/remove that slot; never silently invent an alternative. Only the trainee or their current coach can request new schedule grants. A removed group member can read their own already-issued grant for local recovery but cannot obtain a fresh one. Order deterministically by date, source, and stable ID.
- `record_program_run(operation_id, run_id, grant_id, session_id)` is the idempotent synchronization boundary for online/offline starts. Verify the grant belongs to the authenticated trainee's own historical delivery, then create/return the run; this accepts pre-removal offline work without trusting client timestamps or accepting a fabricated revision/snapshot. Same ID/content returns prior run; changed content fails. Mark completed from session delivery/finish without changing the referenced grant.
- `change_calendar_assignment(operation_id, assignment_id, new_date nullable, cancel boolean)` permits only the assigned coach to move/cancel an upcoming one-off event. It never changes or deletes the fixed workout copy or any session. A pending offline session keeps its local copy and actual completion date; cancellation only removes future planned access.

`assign_workout_template` remains the existing direct-assignment API and still creates an immutable copy. Calendar one-offs call it (with the stable operation ID) and then insert `coach_calendar_assignments` transactionally through a scoped wrapper/RPC, avoiding a half-created event. Program runs do not create/update those standalone assignment copies.

## Effective dates, edits, membership, and offline behavior

- Store dates as `date` and expose `YYYY-MM-DD`; there is no time-of-day event in this scope, so do not convert dates through UTC or DST. Default start date is today's date in the coach's browser calendar when the coach saves/assigns. The trainee sees the same ISO date in their device calendar. If reminders later require a clock time, add an explicit IANA timezone as a separate decision.
- A program slot's offset is `(week_number - 1) * 7 + (day_number - 1)` from the assignment's `start_date`; no locale-dependent weekday conversion. The calendar can show program occurrences by expanding stable slots in the selected range. A group member added mid-cycle joins the next future slot, while keeping the group's shared cycle aligned.
- Saving a new revision replaces every **not-started** future occurrence at next fetch, including those delivered through groups. Saving an included private workout likewise refreshes upcoming grants through the live source reference. A run already started uses its captured grant snapshot through finish/retry. Completed sessions/history never change. A local offline draft is authoritative for that device until it is completed or discarded explicitly; reconciliation must not silently switch its revision.
- Adding a group member joins the current group cycle at its next future slot and grants current program versions. Removing a member immediately prevents fresh schedule grants and hides future group slots. Existing started drafts and offline queue data tied to already-issued grants remain usable and can sync as the trainee's own performed records; no new online starts are allowed after removal. Direct-assignment sources remain independent of group removal.
- If a program definition changes exercise IDs or slot IDs, stable slot IDs keep occurrence identity where semantically continuous; a removed slot cancels only not-started future occurrences. Started/completed run rows remain immutable.
- Group membership changes and group-program pointer changes are all-or-nothing transactions. On rollback, both membership and program delivery remain at the old state. On lost responses, retry with the same operation ID yields the exact prior result. Do not reuse an operation ID for changed members, date, program, or revision. Occurrence grants are durable offline capabilities; retain them while supported clients may have queued work, then prune only with an explicit queue-retention policy.

## Existing UI and client changes

- **Coach Programs** (`src/components/pages/ProgramsPage.tsx`, `src/hooks/usePrograms.ts`): retain existing catalog list/create/delete, add ordered-week editor and workout picker using private workout source; Save shows the revision being activated and how many active individual/group deliveries will read it. Do not use trainee `/programs` tables.
- **Coach Calendar** (`src/components/pages/CalendarPage.tsx`): replace local assignments with `get_client_schedule` and persisted one-off assignment RPC. Keep the current picker; add linked-trainee selection (or an explicit per-client calendar context), event details, and cancel/reschedule for not-started one-off events. Reschedule updates the calendar row only; the fixed-copy workout remains unchanged. Started/completed events cannot be moved/deleted as if they were unperformed.
- **Training Groups** (`src/components/pages/TrainingGroupsPage.tsx`, `useTrainingGroups.ts`): keep group/member CRUD; make selected program/start date a real delivery through `set_group_program`; call `set_training_group_members` for add/remove. Show per-group current program and effective start; membership changes explain the next fetch's delivery consequence.
- **Trainee**: keep personal-program routes unchanged. Add a separate coach-delivery schedule surface reachable from Home/Training, showing source labels “Coach program”, “Group program”, or “One-off workout”. Launch an upcoming program occurrence from the latest resolved revision; launch/resume an existing run from its saved snapshot. Extend `useAssignedWorkout`/`GymLogger` to accept this snapshot source while preserving existing direct assigned-workout loading. Persist run/snapshot in the existing account-scoped draft and enqueue it with the session so parent-session acknowledgement remains before child set-log acknowledgement.
- Show actionable load errors/retry and honest no-assignment states. Coach programs, groups, and calendar are available as V1 deterministic flows; AI stays clearly unavailable. Do not add social exposure as a side effect.

## Acceptance and rollout

Database/RPC tests: coach/current-trainee ownership; role/cross-coach denial; stale revision write; fixed-operation exact retry and changed-content rejection; save revision/source-workout edit changes future grants but not started snapshots; membership add/remove/re-add; group/program save atomic rollback; shared direct/group delivery source retention; stable date/slot expansion over month/year/DST boundaries; one-off immutable source copy; cancel/reschedule constraints; historical and pending data survives update/removal; RLS of another trainee's schedule; operation retry and concurrent revision/member update.

Web/mobile focused checks: save a program, assign directly and through a group, update its source and observe upcoming revision update; start one run, update the program, and verify current run retains old snapshot while next occurrence uses new; remove a group member with active offline draft, reconnect, and verify one exact session/sets sync without restoring future access; one-off event persists after refresh and its prescription stays fixed after source edit; two accounts never see each other's schedule. Later, run coordinated TRACE and TRACE-client suites/types/contracts after the implementation interfaces settle. Do not treat local tests as hosted/device acceptance.

Deploy additive schema and RPCs before web/mobile consumers. Backfill old group links from migration effective date. Rollback disables new write/read RPCs and restores previous client route behavior; retain new revision/delivery/run rows and all session/outbox data for forward recovery rather than deleting user records. If reverting while a client build has written program-run fields, keep nullable columns/RPC compatibility until that build is retired. Android signing, physical-device acceptance, and distribution are expressly deferred until app code completion; they remain later release gates.

## Decisions still needed before implementation

- Which role can author coach programs in the current schema: this design assumes only coaches using existing `public.programs`; trainee personal `workout_programs` remain separate.
- Whether an archived source workout should block archive until all active program slots are replaced: proposed behavior is block archive, with an explicit replace/remove-in-program flow.
- Whether revisions may remove/replace a slot after its date has passed: proposed behavior is future not-started occurrences update; past dates and any started/completed runs remain immutable.
- Whether coach calendar one-offs should support multiple recipients at once: smallest slice is one recipient per event; group program delivery is the only bulk path.
- Offline concurrent starts of the same program occurrence on two devices: keep both real session IDs and performed logs, identify them as separate runs, and never discard either. The product may later add a conflict/review UI if this occurs often.
