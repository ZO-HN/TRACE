## TRACE fit and operating shape

The current TRACE schema already has `public.exercises` with name, target muscle group, equipment type, custom/creator fields and a `reference_video_url`; a later migration adds description, category, exercise type, movement fields, coaching cues, equipment tags, and the normalized `exercise_muscles` relation. Authenticated users have shared catalog reads. That is enough to evaluate an import mapping, but it does not provide explicit source, external source ID, per-asset license/attribution, or media provenance fields. These would need an accepted data-contract decision before a durable import; do not overload `reference_video_url` with unreviewed hosted media.

Recommended next-stage design, if separately authorized: curate a subset once, retain each source's stable ID and source URL plus per-record/media attribution/license and review state, normalize/dedupe into the shared exercise catalog, and present paginated/searchable list and detail views. Avoid copying a full catalog per coach/user. Fetch or cache optimized media only for items whose rights expressly allow the intended display, storage, and commercial use; otherwise link to provider pages or omit media. Do not make GitHub raw URLs, CDN paths, or a free API a runtime dependency: availability, rate limits, URL stability, content changes, and terms are outside TRACE's control. Do not assume a free API is free for commercial use or permits persistence.

For storage planning only, an illustrative estimate is `number of retained clips × average encoded bytes per clip`: e.g. 200 curated clips × 1 MB each ≈ 200 MB before replicas/backups/request delivery. This is arithmetic, not a measurement of any candidate's actual media; measure selected files before sizing storage. Start with metadata and a small rights-cleared visual subset to control storage and bandwidth.
