Status: implemented locally; core aggregate checks passed, later follow-ups remain separately tracked; not deployed or accepted on a device. Owner: TRACE maintainers. Date: 2026-11-07 SGT. Scope: the saved-meal repair in phase 3 and the owner's subsequent request to include full coach meal-plan delivery in the [completion plan](../planning/client-workflow-completion-plan-2026-11-06.md).

## Personal saved meals

`20261107010000_atomic_saved_meals.sql` adds `save_personal_meal` and a private receipt ledger. A matching authenticated trainee creates the meal, ordered food snapshots and operation receipt in one transaction. Replays require identical content and ownership; a receipt cannot recreate a deleted meal. Invalid names, quantities, duplicate child IDs or an existing template identity roll back the entire write. Existing meal tables/read paths remain compatible.

The mobile caller persists the account-scoped operation/template/item IDs before sending. A lost response can be retried after screen/device restart using **Retry previous meal save**; changing content cannot silently reuse an uncertain operation. A failed receipt cleanup does not turn a confirmed server save into an apparent failure. Saved-meal macros use their existing `numeric(6,2)` storage bounds (0–9999.99, two decimals); unsupported precision is rejected, apart from floating-point representation noise canonicalized before serialization. Calories are non-negative integers. No historical intake is recalculated.

**Log all** validates the whole meal and inserts all nutrition queue rows through one exclusive SQLite transaction, then updates the UI mirror. A failed batch reports no food as saved. Retries retain the same per-item IDs and original timestamp, reconcile an identical already-committed batch, and reject conflicting IDs. Cloud delivery remains per record, with pending/failed states; device persistence is not an atomic cloud nutrition transaction. The storage backend must support atomic insertion; there is no partial-write fallback. Native SQLite rollback/restart acceptance is still required.

## Coach publication and trainee readback

`20261107020000_publish_meal_plans.sql` adds immutable publications, distinct from editable coach `meal_plans`. **Save meal plan draft** does not assign it. The coach explicitly chooses a currently linked trainee and start date, then publishes a fixed copy with stable operation identity. The server checks the draft snapshot and copies its real coach-owned foods, explicit catalog serving labels and quantities. Foreign/missing foods, incomplete macros, invalid serving quantities, unsupported targets and changed drafts fail before publication.

A plan contains 1–31 listed days, 1–20 meals per day, 1–50 foods per meal and at most 500 foods overall. Days run once in listed order from the chosen local calendar date; there is no implicit repeat/calendar expansion. Serving quantities multiply that food's labeled catalog serving, support up to 100 with three decimals, and do not imply gram/unit conversion. Scaled macros are rounded to the intake schema's tenths of grams, calories to whole kcal. The publication retains those values and labels when foods or drafts later change or disappear. One explicit calorie target is retained; each day's meal-derived macro/energy totals remain separately visible rather than being silently forced to that target.

For a date, the newest applicable publication from the trainee's current coach replaces older publications. Future publications do not replace the current one early. If the applicable plan's listed days have ended, the UI reports that it ended rather than reverting to an older plan or repeating it. Older publications and actual logged intake are retained. Trainees can read their own history; a coach can read only their publications while that trainee remains linked. Raw source-builder data is not granted to client readers or returned by the current-plan RPC.

The Nutrition screen loads the exact published copy on focus/refresh, shows its publication identity/date, serving details, target and planned totals beside actual intake, and distinguishes missing/error/loading/cached/ended states. An account-scoped cached copy supports previously downloaded offline reading, labeled as potentially outdated. Assignment never marks food as eaten: **Log [meal] as eaten today** is an explicit atomic device queue action. Signing/device work is deferred by owner instruction until application completion, not waived.
