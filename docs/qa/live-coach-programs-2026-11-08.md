## End-to-end local implementation

1. In coach Programs, create/select the coach catalog record and **Edit days and delivery**. Add up to 366 explicitly labeled days, unique day numbers 1–366 and either an owned active private workout or a rest day. Stable slot IDs survive ordinary edits. Saving activates a revision immediately for existing deliveries; there is no separate per-recipient republish step. Unsaved day edits must be saved or explicitly reloaded before changing delivery, preventing a delivery refresh from discarding them.
2. Select a currently linked trainee or owned group, choose its local start date, and save **Active delivery**. A group uses one aligned shared cycle. Its membership is resolved at read/open time; adding/removing members changes fresh access without copying an entire plan per member. A program choice in the older Create Group dialog remains metadata until this explicit activation/date step. Changing a configured group's program through the older metadata path pauses the mismatched delivery until reconfigured; it never silently delivers an unauthorized program.
3. Coach Calendar, after selecting a trainee, reads their current program/group dates alongside its saved one-off list. Trainee Training shows the same weekly planning metadata. Day offsets are date-only arithmetic from the anchor, including leap/month/year boundaries. Listed days run once; there is no implicit repeat. Dates are planning labels, and listed past/future days may be opened for catch-up/early training; there is no clock-based start authorization. Already performed history remains independent.
4. Merely viewing a week creates **no workout copies**. **Open program workout** checks the current coach, delivery, membership, revision and private source, then atomically issues an immutable assigned prescription. Different operation IDs reuse the same matching grant for the trainee/program/anchor/slot/revision/content. A fingerprint indexes candidates; full snapshot equality is authoritative. An indexed collision fails rather than using different content. Private raw snapshots and receipt tables are not client-readable/writable.
5. The mobile caller persists its account-scoped open request before the RPC, so a lost response/device restart can use **Confirm previous program open** with identical IDs and content. A changed pending request is blocked. A confirmed server revision/authorization error clears only the rolled-back request; unknown outcomes retain it. The returned exact template ID launches the existing session logger, caches, stable set IDs and durable outbox. The existing `workout_sessions` row remains the performed record; no parallel program-run/session store was introduced.

## Update, removal and historical boundaries

Program revision edits and current private-source edits affect subsequent fresh opens through existing deliveries. A stale revision from an online schedule cannot silently start a different revision: it fails and asks for reload. Each issued copy remains immutable, including source values, repeated exercise positions and zero rest. An old receipt may be confirmed after update/removal/deletion; this confirms its original owned result and does not grant a new revision. Started drafts and existing queued sessions keep their exact copy and can sync later.

An inactive direct delivery stops that source. A group removal, group deletion, mismatched program pointer or program deletion stops fresh group delivery. Independent direct/group sources remain effective; matching program/anchor/slot entries combine instead of appearing twice. Already-issued copies are durable recovery capabilities: the service cannot retrospectively know which offline copy was started, so it retains them rather than discarding local work or claiming perfect offline revocation. Newer clients exclude program copies from the ordinary standalone workout list/default selection; exact IDs remain available for draft/history recovery. Older compatible clients may still list these owned copies and require acceptance against the intended supported build.

Program schedules cache only account/current-coach/date-range metadata, label offline freshness, and never substitute old cache after an online failure. Offline opening requires an already-issued matching-revision grant and a previously downloaded workout prescription; metadata alone is not a full offline workout download. Resume existing drafts before opening another version. These are source/test boundaries, not native force-kill/SQLite acceptance.

Coach program heads/deliveries are RPC-writable only, with expected revisions and exact operation receipts. Coach-only version history is retained if a program is deleted. Current membership/link checks and private-source ownership guard fresh opens; foreign/forged recipients/sources are denied. Legacy group writes remain compatible but validate that program/member ownership matches the group's coach. No personal `workout_programs` / `program_days` / share-token behavior was repurposed.

The actual group member consumer now keys state by coach/group, cancels old reads, avoids repeated requests caused by changing callback identity, serializes toggles and exposes read/write errors. After an uncertain membership mutation it requires a fresh member read rather than assuming success or blindly duplicating an add. This is separate from earlier hook-only D04 evidence.
