## Implemented boundary

The coach Calendar route now selects a linked trainee, real saved private workout and date, then uses `schedule_coach_workout` to commit the immutable assignment copy and dated calendar row together. Reload/month/trainee selection reads persisted rows, paging beyond 200 instead of losing events or silently truncating a busy month. This replaces the former memory-only calendar. Date values are ISO local calendar labels with no implicit UTC conversion or time-of-day/reminder semantics. These one-off copies keep the approved standalone fixed-copy policy; source edits never change them.

`change_coach_calendar` supports revision-checked moves and irreversible planned cancellation. Exact operation receipts recover lost responses; changed operation content is rejected. A session already recorded against the template blocks move/cancel. An unreported offline start cannot be known by the server: a concurrent cancellation removes future planning visibility but never deletes the copy, draft or later synced session. Calendar dates/cancellation are planning state, not retrospective template-access revocation. Templates remain in the trainee's existing library; this is explicit, not an enforcement claim.

RLS grants the trainee their own calendar history; coach reads/changes require the original coach and current trainee link. Private original request/snapshot data is not granted to readers. Public, anonymous and direct client writes are denied. A changed source or failed event insert rolls back the entire assignment operation. Replays bind exact event/copy/source/recipient/date/snapshot and owner; operation IDs cannot replace content. The coach UI holds pending request input and retries its exact payload while mounted. Browser reload does not persist pending IDs: inspect the saved calendar/library before recreating an uncertain operation.

The trainee Training screen shows weekly current-coach assignments and launches the exact immutable `template_id` through the existing session route. It separates loading/error/empty/explicit offline cache. Cache keys include trainee, coach and date range; an online failure never silently substitutes cached content. Cached dates/cancellations are labeled potentially outdated. Schedule metadata does not itself download exercise prescriptions: initial workout opening requires a connection, with existing exact-template caches/draft recovery handling later offline use. Personal programs and standalone workout logging remain separate.

The same mobile follow-up makes a corrupt/pending saved-meal request visible before any food is logged and clears the prior-save warning after confirmed normal/recovery saves. This changes no stored intake or prior operation identity.
